# ADR.md --- Architecture Decision Record

## 목적

이 문서는 프로젝트의 주요 아키텍처 및 기술적 의사결정을 기록한다.
SYSTEM_ARCHITECTURE.md가 시스템 구조(What)를 설명한다면, ADR은 설계
이유(Why)를 기록한다.

------------------------------------------------------------------------

## ADR-001 Outlook COM 사용

**결정**: Outlook 2019 Desktop COM(Object Model) 사용

**이유** - Outlook 2019 Desktop 환경과 가장 잘 맞음 - 기존 업무 흐름
변경 없음 - 받은편지함 직접 조회 가능 - .msg 저장 불필요

**대안** - Microsoft Graph API - Power Automate - .msg 분석

------------------------------------------------------------------------

## ADR-002 받은편지함 직접 조회

**결정**: 날짜 + 등록 담당자 기준으로 받은편지함을 일괄 조회

**이유** - 메일 제목이 통일되어 있지 않음 - 담당자 기준이 가장 안정적

------------------------------------------------------------------------

## ADR-003 Read Only 정책

**결정**: 메일은 읽기만 한다.

**이유** - 삭제·이동·읽음 변경 방지 - 업무 안정성 확보

------------------------------------------------------------------------

## ADR-004 Rule Engine 우선

**결정**: 규칙 기반 분석을 기본으로 사용

**이유** - 보안 - 재현성 - 비용 절감

------------------------------------------------------------------------

## ADR-005 검토 후 Excel 반영

**결정**: 자동 반영 대신 검토 화면 제공

**이유** - 메일 형식 편차 대응 - 오입력 방지

------------------------------------------------------------------------

## ADR-006 원본 데이터 시트 저장

**결정**: Excel 원본 데이터 시트에 저장하고 기존 집계표는 참조

**이유** - 유지보수 용이 - 재집계 가능

------------------------------------------------------------------------

## ADR-007 중복 처리

**결정**: Outlook EntryID + 업무 키 사용

업무 키 - 보고일 - 작성자 - Tracking No. - 장비명 - 업체명

------------------------------------------------------------------------

## ADR-008 SQLite 사용

**결정**: SQLite 채택

**이유** - 서버 불필요 - 배포 간단 - 로그·설정 관리 적합

------------------------------------------------------------------------

## ADR-009 계층형 아키텍처

**결정** - Presentation - Application - Domain - Infrastructure

**이유** - 테스트 및 유지보수 용이

------------------------------------------------------------------------

## ADR-010 단계적 개발

**결정** PoC → 추출기 → 검토 → Excel 연동 → 자동화

**이유** - 리스크 최소화 - 실제 메일 기반 규칙 보완

------------------------------------------------------------------------
