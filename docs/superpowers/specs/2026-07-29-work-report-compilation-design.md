# 전장 외주 공수표 취합·검토·복사 설계

## 1. 배경과 목표

현재 애플리케이션은 Outlook 업무보고 메일을 수집·추출하고 사용자가 행을 검토하는
기능까지 제공하지만, 여러 메일의 외주 공수 내역을 하나의 최종 보고 표로 취합하는
기능은 없다.

이번 기능은 메일에서 추출한 외주 작업 행과 사용자가 추가한 예외 행을 검증하고,
투입 공수와 누적 공수를 계산·대조한 뒤, 사용자가 최종 확인한 표를 Outlook 메일
본문에 붙여넣을 수 있도록 클립보드에 복사하는 것을 목표로 한다.

기본 업무 흐름은 전날 퇴근 전 도착한 업무보고 메일을 다음 날 아침 취합하는
방식이다. 다만 처리일과 작업일은 별개이며, 최종 보고에는 하루 이상의 작업일을
포함할 수 있다.

## 2. 범위

### 2.1 포함 범위

- 메일 제목·본문·수신일을 이용한 작업일 판정과 불일치 경고
- 상세 외주 공수 행의 취합 및 사용자 검토
- 실제 작업인원, 인당 공수, 투입 공수, 누적 공수의 분리 저장
- 투입 공수와 누적 공수의 자동 계산 및 메일 보고값 대조
- `업체 + Tracking No.` 기준 누적 공수 연결
- Tracking No.가 없을 때 정규화한 장비명을 보완 키로 사용
- 주말·예외 작업을 위한 수동 행 추가
- 정상 행 자동 포함, 문제 행 개별 검토, 전체 최종 확인
- 작업일별 머리글을 반복하는 최종 표 미리보기
- HTML 및 일반 텍스트 클립보드 복사
- 최종 확정 보고서 스냅샷과 변경 이력 저장

### 2.2 제외 범위

- 메일 상단의 본사·안산 업체별 인원 요약표
- 카카오톡 메시지 자동 수집
- 지역, 제작 장소 또는 장비별 지역 자동 분류
- Outlook 초안 생성, 자동 회신·전달 또는 발송
- Excel COM 쓰기와 기존 Excel 내보내기 기능 변경
- 외부 AI 또는 외부 서버로 메일 데이터 전송

## 3. 선택한 접근법

기존 검토 화면을 확장하고 그 뒤에 최종 미리보기 단계를 추가한다. 별도 취합
프로그램이나 임시 Excel 파일을 만들지 않는다.

이 접근법은 이미 구현된 Outlook 수집, 파싱, 검토 상태, SQLite 저장 구조를
재사용하면서도 계산과 최종 보고 생성을 application 서비스로 분리할 수 있다.
UI는 계산 규칙을 직접 구현하지 않고 서비스의 결과와 경고 상태만 표시한다.

## 4. 아키텍처

### 4.1 기존 구성 요소

`ExtractionOrchestrator`는 현재의
`normalize → split_sections → extract_work_records → validate` 흐름과 Outlook
EntryID 보존을 유지한다. 메일 원문에서 추출한 값은 추정하거나 덮어쓰지 않는다.

기존 `ReviewStatus`를 검토 상태의 기준으로 사용한다. 취합 기능만을 위한 별도의
중복 상태 문자열 체계를 만들지 않고, 경고 코드와 포함 여부를 별도 속성으로 둔다.

### 4.2 신규 application 서비스

`ManDayCalculationService`:

- 순수한 Decimal 계산과 값 대조를 담당한다.
- Outlook, PySide6, SQLite에 의존하지 않는다.
- 메일 보고값, 프로그램 계산값, 사용자 확정값을 각각 반환한다.
- 누적 선행 행이 없을 때 값을 추정하지 않는다.

`WorkReportService`:

- 메일 추출 행과 수동 행을 동일한 취합 행으로 변환한다.
- 작업일 판정, 누적 키 생성, 중복 검출, 포함 여부와 검토 가능 상태를 관리한다.
- 사용자 수정·확인 후 영향받는 미확정 후속 누적 행을 다시 계산한다.
- 이미 최종 확정된 과거 보고서 스냅샷은 변경하지 않는다.

`FinalReportService`:

- 포함 행의 차단 오류와 미확정 경고를 검사한다.
- 승인된 정렬 규칙으로 행을 정렬한다.
- 전체 최종 확인 시 보고서와 행 스냅샷을 저장한다.
- 확정 후 원본 행이 바뀌면 현재 작업 보고서의 확정을 무효화한다.

`HtmlReportRenderer`:

- 동일한 스냅샷에서 HTML 표와 일반 텍스트 표를 생성한다.
- Outlook COM이나 Excel COM을 사용하지 않는다.
- 클립보드는 HTML 형식을 우선하고 일반 텍스트를 대체 형식으로 함께 제공한다.

### 4.3 UI

현재 `MainWindow`와 리뷰 그리드를 확장한다.

- 작업일
- 업체명
- Tracking No.
- 장비명
- 사업팀
- 실제 작업인원
- 인당 공수
- 메일 투입 공수·계산 투입 공수·확정 투입 공수
- 메일 누적 공수·계산 누적 공수·확정 누적 공수
- 검증 상태와 포함 여부

주요 동작은 `수동 행 추가`, `문제 행 확인`, `반영 제외`, `최종 표 미리보기`,
`전체 최종 확인`, `표 복사`이다.

## 5. 취합 행 데이터 모델

논리 모델 `WorkReportRow`는 다음 정보를 분리해 가진다.

- 식별: 내부 행 ID, 원본 Outlook EntryID, 원본 추출 레코드 ID
- 출처: `MAIL` 또는 `MANUAL`
- 작업: 작업일, 업체명, Tracking No., 장비명, 사업팀
- 인원: `actual_headcount`
- 인당 공수: `per_person_man_day`
- 투입 공수: `reported_daily_man_day`, `calculated_daily_man_day`,
  `confirmed_daily_man_day`
- 누적 공수: `reported_cumulative_man_day`,
  `calculated_cumulative_man_day`, `confirmed_cumulative_man_day`
- 검토: 경고 코드 목록, `ReviewStatus`, 포함 여부
- 이력: 수정 사유, 확인 시각, 생성·수정 시각

기존 도메인의 다음 필드는 계속 서로 합치지 않는다.

- `actual_headcount`
- `per_person_man_day`
- `daily_man_day`
- `cumulative_man_day`
- `day_man_day`
- `night_man_day`

메일 보고값과 계산값은 보존하고, 사용자가 확정한 값만 최종 표에 사용한다. 불일치
해결 과정에서도 원래 보고값을 덮어쓰지 않는다.

## 6. 공수 계산 규칙

모든 공수 계산은 이진 부동소수점 대신 `Decimal`을 사용한다.

### 6.1 투입 공수

```text
계산 투입 공수 = 실제 작업인원 × 인당 공수
```

- 메일에 투입 공수가 있으면 메일 보고값을 최초 확정 후보로 사용한다.
- 메일에 투입 공수가 없으면 계산값을 확정 후보로 사용하고
  `투입 공수 미기재` 경고를 표시한다.
- 메일 보고값과 계산값이 다르면 두 값을 모두 보여주고
  `투입 공수 불일치` 경고를 표시한다.
- 불일치 행은 사용자가 확정값을 선택하거나 수정하기 전까지 최종 확정할 수 없다.

### 6.2 누적 공수

누적 계열 키는 다음과 같다.

```text
기본 키 = 정규화 업체명 + Tracking No.
보완 키 = 정규화 업체명 + 정규화 장비명
```

Tracking No.가 있으면 반드시 기본 키를 사용한다. Tracking No.가 없을 때만 장비명을
사용한다. 두 값이 모두 없으면 계열을 식별할 수 없으므로 차단 오류로 처리한다.

```text
계산 누적 공수 = 직전 확정 누적 공수 + 현재 확정 투입 공수
```

- 메일 누적값이 없고 직전 확정 누적값이 있으면 자동 계산하고
  `누적 공수 미기재` 경고를 표시한다.
- 메일 누적값과 계산 누적값이 다르면 `누적 공수 불일치` 경고를 표시한다.
- 계열의 첫 행에 메일 누적값이 있으면 `최초 누적 기준 확인`을 표시하고 사용자가
  해당 값을 최초 확정 기준으로 승인한다.
- 계열의 첫 행에 메일 누적값도 이전 기준값도 없으면 값을 추정하지 않는다.
  사용자가 기준 누적값을 입력·확정할 때까지 차단한다.
- 과거 미확정 행의 확정값이 바뀌면 같은 계열의 후속 미확정 행을 다시 계산한다.
- 최종 확정된 보고서 스냅샷은 재계산하지 않는다.

### 6.3 표시 형식

- 실제 작업인원은 정수로 표시한다.
- 공수는 소수점 한 자리로 표시한다.
- 내부 계산값은 Decimal로 유지하고 표시 경계에서 `0.1` 단위로 양자화한다.
- 반올림은 정확히 중간인 값을 0에서 멀어지는 방향으로 처리하는
  `ROUND_HALF_UP`을 사용한다.

## 7. 작업일 판정

작업일 판정에는 메일 제목, 본문, Outlook 수신일, 처리일을 사용한다.

우선순위는 다음과 같다.

1. 제목에서 인식한 날짜를 작업일로 사용한다.
2. 본문 날짜는 교차 검증에 사용한다.
3. 수신일은 통상적인 전날 보고 흐름을 확인하는 보조 근거로 사용한다.
4. 처리일은 조회·취합 기준일이며 작업일로 자동 대입하지 않는다.

제목 날짜와 본문 또는 수신 흐름이 다르면 제목 날짜를 유지하면서
`작업일 불일치 · 확인 필요` 경고를 표시한다. 사용자가 작업일을 수정하면 변경
전후 값과 사유를 기록한다.

제목에 날짜가 없으면 본문 날짜를 후보로 제시하되 자동 확정하지 않는다. 제목과
본문 모두 날짜가 없으면 수신일로 작업일을 추정하지 않고 사용자 확인을 요구한다.

## 8. 중복·수정 보고 처리

동일한 다음 조합은 정상적으로 두 번 발생하지 않는 것으로 간주한다.

```text
작업일 + 정규화 업체명 + Tracking No.
```

Tracking No.가 없는 행은 정규화 장비명을 보완 식별자로 사용한다.

같은 조합이 둘 이상이면 자동 합산하지 않고 중복 또는 수정 보고로 표시한다.
사용자는 기존 행과 새 행의 주요 값을 비교한 뒤 다음 중 하나를 선택한다.

- 새 보고로 교체
- 기존 보고 유지
- 두 행 모두 제외하고 수동 행 작성

중복이 해결되지 않은 상태에서는 최종 보고를 확정할 수 없다. 교체를 선택해도 원본
행과 선택 이력은 삭제하지 않는다.

## 9. 검토 및 최종 확정 흐름

1. Outlook에서 메일을 읽기 전용으로 수집한다.
2. 추출 행을 취합 행으로 변환하고 계산·검증한다.
3. 정상 행은 기본적으로 포함한다.
4. 문제 행은 사용자가 개별 검토한다.
5. 주말·예외 작업은 `수동 행 추가`로 입력한다.
6. 수동 행에도 같은 계산·중복·누적 규칙을 적용한다.
7. 모든 차단 오류와 필수 확인이 해소되면 최종 미리보기를 연다.
8. 사용자가 전체 표를 확인하고 `전체 최종 확인`을 실행한다.
9. 확정된 스냅샷을 HTML·일반 텍스트 형식으로 클립보드에 복사한다.
10. 사용자가 Outlook 메일 본문에 직접 붙여넣고 발송한다.

최종 확정 조건:

- 정상 행은 자동 포함 또는 명시적 제외 상태이다.
- 모든 경고 행이 개별 확인되었다.
- 해결되지 않은 중복과 차단 오류가 없다.
- 최종 미리보기의 전체 확인이 완료되었다.

최종 확인 후 현재 보고서의 값, 포함 여부 또는 정렬에 영향을 주는 정보가 바뀌면
기존 최종 확인을 자동 취소하고 전체 확인을 다시 요구한다.

## 10. 최종 표 구성

표의 열은 다음 순서를 사용한다.

1. 일자
2. 거래처명
3. Tracking No.
4. 장비명
5. 사업팀
6. 실제 작업인원
7. 인당 공수
8. 투입 공수
9. 누적 공수

정렬 규칙:

1. 작업일 오름차순
2. 같은 작업일 안에서 업체 설정 순서
3. 같은 업체 안에서 Tracking No. 오름차순
4. Tracking No.가 없으면 장비명 오름차순

작업일이 바뀌는 지점마다 열 머리글을 다시 출력한다. 제목은 포함된 작업일이
하루면 단일 날짜, 여러 날이면 시작일과 종료일 범위를 표시한다.

최종 표에는 `confirmed_daily_man_day`와 `confirmed_cumulative_man_day`만 출력한다.
경고와 내부 계산 근거는 검토 화면에만 표시한다.

## 11. 경고와 차단 기준

### 11.1 개별 확인이 필요한 경고

- 작업일 불일치
- 투입 공수 미기재
- 투입 공수 불일치
- 누적 공수 미기재
- 누적 공수 불일치
- 최초 누적 기준 확인

### 11.2 최종 확정을 차단하는 상태

- 필수 숫자 값이 유효하지 않음
- 실제 작업인원이 정수가 아니거나 음수임
- 공수 값이 음수임
- Tracking No.와 장비명이 모두 없음
- 최초 누적 기준을 계산하거나 확인할 수 없음
- 중복·수정 보고가 해결되지 않음
- 경고 행의 개별 검토가 끝나지 않음

경고를 확인했다는 사실만으로 값을 자동 수정하지 않는다. 사용자 확정값이 명시되어야
한다.

## 12. 영속성과 감사 이력

신규 저장 구조는 다음 논리 단위를 제공한다.

- 현재 취합 행
- 누적 계열별 최신 확정 기준점
- 최종 보고서
- 최종 보고서 행 스냅샷
- 검토·수정·확정 action log

DB 스키마 변경은 기존 DB를 파괴하지 않는 additive migration으로 구현한다.
앱 시작 시 구버전 스키마를 인식하고 필요한 테이블·열·인덱스를 추가한다. 기존
`processed_mails`, `extracted_records`, `action_logs` 데이터와 호환성을 유지한다.

감사 이력에는 다음을 저장한다.

- Outlook EntryID 또는 안전한 내부 참조
- 자동 계산값, 메일 보고값, 사용자 확정값
- 수동 행 추가와 수정 전후 값
- 수정 사유
- 경고 확인 시각과 처리 결과
- 중복·수정 보고 선택 결과
- 최종 표 확인·복사 시각

메일 본문 전체, 전체 수신자 목록, 불필요한 개인정보는 저장하거나 로그에 출력하지
않는다. 원문 근거가 필요하면 판단에 필요한 최소 구간만 보존한다.

## 13. 오류 처리

- Outlook 연결 실패: 기존 화면 값을 유지하고 읽기 전용 연결 안내를 표시한다.
- 개별 메일 읽기·파싱 실패: 나머지 메일을 계속 처리하고 실패 메일만 문제 목록에
  표시한다.
- 계산 입력 오류: 해당 행을 차단하고 사용자가 원문 또는 값을 확인하게 한다.
- DB 저장 실패: 트랜잭션을 롤백하고 확정·복사 완료 상태를 기록하지 않는다.
- 클립보드 복사 실패: 최종 스냅샷은 유지하고 재복사할 수 있게 오류를 표시한다.
- 보고서 확정 후 원본 변경: 현재 작업 보고서의 확정 상태만 취소하고 과거 확정
  스냅샷은 유지한다.

## 14. 테스트 전략

### 14.1 계산 단위 테스트

- 실제 작업인원과 인당 공수의 Decimal 곱셈
- 투입 공수 미기재 자동 계산
- 메일 투입 공수와 계산값 불일치
- 누적 공수 미기재 자동 계산
- 메일 누적값과 계산 누적값 불일치
- 최초 누적 기준 승인 및 기준 부재 차단
- 소수점 한 자리 표시와 확정된 반올림 규칙

### 14.2 날짜·식별 테스트

- 제목 날짜 우선 적용
- 제목·본문·수신 흐름 불일치 경고
- 제목 날짜 부재 시 자동 확정 방지
- 업체와 Tracking No.를 사용한 누적 연결
- Tracking No. 부재 시 장비명 보완
- 동일 작업일·업체·Tracking No. 중복 차단

### 14.3 업무 흐름 테스트

- 정상 행 자동 포함
- 문제 행 개별 검토 전 최종 확정 차단
- 수동 행에 동일 계산·검증 적용
- 값 변경 시 현재 보고서의 최종 확인 취소
- 최종 보고서 스냅샷 불변성
- 앱 재시작 후 검토·확정 상태 복원
- 선행 확정값 변경 후 후속 미확정 누적 재계산

### 14.4 출력 테스트

- 작업일, 업체 설정 순서, Tracking No. 순 정렬
- 날짜가 바뀔 때 열 머리글 반복
- HTML 표와 일반 텍스트 표의 값 일치
- 최종 표가 확정값만 사용하는지 확인
- 클립보드 payload 생성

### 14.5 회귀·안전 테스트

- 익명화한 Python 문자열 fixture만 사용
- 기존 파싱·검토 기능 전체 회귀
- 구버전 DB에서 신규 스키마 migration
- Outlook 읽기 전용 mock 경계 유지
- 메일 원문 전체가 DB나 로그에 저장되지 않음

실제 Outlook 수집, Windows 클립보드 형식, Outlook 본문 붙여넣기 모양은 자동
단위 테스트와 분리한다. 구현 완료 후 사용자의 명시적 승인 아래 테스트 메일과
복사본으로만 실환경 검증한다.

## 15. 완료 조건

- 메일 및 수동 행을 하나의 상세 외주 공수표로 취합할 수 있다.
- 제목 날짜를 우선 사용하고 다른 날짜 근거와의 불일치를 경고한다.
- 투입 공수와 누적 공수의 보고값·계산값·확정값이 분리되어 보존된다.
- 누적 공수 누락과 계산 불일치를 자동으로 발견한다.
- 최초 누적 기준과 중복·수정 보고를 사용자가 명시적으로 해결할 수 있다.
- 정상 행 자동 포함, 문제 행 개별 검토, 전체 최종 확인 흐름이 동작한다.
- 여러 작업일을 정해진 순서와 반복 머리글로 미리볼 수 있다.
- 최종 확정 스냅샷을 HTML·일반 텍스트로 복사할 수 있다.
- Outlook은 읽기 전용이며 자동 초안·발송을 하지 않는다.
- 기존 DB와 파싱·검토 기능의 회귀 테스트가 통과한다.
