# rules.md — 개발 규칙

## 1. 최우선 원칙

1. 데이터 정확성이 자동화율보다 우선한다.
2. 불확실한 값은 추정하지 않는다.
3. Outlook 메일은 읽기 전용으로 다룬다.
4. 사용자의 승인 전에는 Excel에 반영하지 않는다.
5. Excel 반영 전 백업을 반드시 만든다.
6. 성공적으로 저장되기 전에는 처리 완료로 기록하지 않는다.
7. 외부 AI와 외부 서버 전송은 기본 금지한다.

---

## 2. 범위 규칙

### 허용

- Outlook 받은편지함 또는 지정 폴더 읽기
- 제목·발신자·수신일·본문·EntryID 읽기
- 원본 메일 열기
- 로컬 추출·검토
- Excel 테스트 사본 및 승인된 실제 파일 쓰기
- SQLite 처리 이력 저장

### 금지

- 메일 삭제
- 메일 이동
- 읽음/안읽음 변경
- 자동 회신
- 자동 전달
- 첨부파일 외부 업로드
- 검토 없는 자동 Excel 반영
- 원본 Excel 무백업 수정
- 불명확한 숫자 의미 추정
- 하드코딩된 실제 사용자·업체 데이터 커밋

---

## 3. 아키텍처 규칙

- presentation, application, domain, infrastructure 계층을 분리한다.
- UI는 COM 객체를 직접 다루지 않는다.
- parser는 Outlook 객체를 직접 다루지 않는다.
- Excel adapter는 도메인 추출 로직을 포함하지 않는다.
- domain 모델은 PySide6, pywin32, pandas에 의존하지 않는다.
- infrastructure 예외는 application 수준 예외로 변환한다.
- COM 객체는 스레드 간 전달하지 않는다.
- 의존성은 생성자 주입을 우선한다.

---

## 4. 코드 규칙

- Python 3.12 기준
- 모든 공개 함수에 타입 힌트 사용
- 복잡한 공개 함수·클래스에 docstring 작성
- 함수는 한 가지 책임만 수행
- 50줄을 크게 넘는 함수는 분리 검토
- broad `except Exception`으로 오류를 삼키지 않음
- 로그를 남기고 필요한 경우 다시 raise
- magic number와 magic string 금지
- Enum 또는 상수 모듈 사용
- 경로는 pathlib 사용
- 날짜는 timezone-aware datetime을 우선
- 돈·공수와 같은 소수는 필요 시 Decimal 사용 검토
- 사용자 메시지는 한국어
- 내부 변수·함수명은 영어

---

## 5. 데이터 규칙

### 필드 분리

다음 값은 절대 같은 필드로 합치지 않는다.

- actual_headcount
- per_person_man_day
- daily_man_day
- cumulative_man_day
- day_man_day
- night_man_day

### 원문 보존

- 메일 원문 전체는 DB에 장기 저장하지 않는 것을 기본으로 한다.
- 분석 근거가 필요한 경우 장비 구간 원문만 제한적으로 저장한다.
- 로그에 메일 본문 전체를 기록하지 않는다.

### 정규화

- 이메일 주소는 소문자
- Tracking No.는 공백 제거 및 대문자
- 업체명은 canonical name으로 변환
- 장비명은 원문과 정규화 값을 모두 보유 가능
- 빈 문자열은 None으로 처리

---

## 6. 추출 규칙

1. 장비 구간을 먼저 나눈 뒤 외주 데이터를 추출한다.
2. 메일 전체에서 업체·숫자만 일괄 추출하지 않는다.
3. 업체 마스터와 별칭을 우선 사용한다.
4. 레이블과 값의 거리, 같은 줄 여부, 장비 구간 위치를 함께 평가한다.
5. `누적`, `누계` 인접 숫자는 누적 후보로 분류한다.
6. `주간`, `야간`, `당일` 인접 숫자는 당일 후보로 분류한다.
7. 숫자 크기만으로 의미를 판단하지 않는다.
8. 후보가 여러 개이고 우선순위를 결정할 수 없으면 검토 필요로 남긴다.
9. `전일과 동일`은 자동으로 전일 데이터를 복사하지 않는다.
10. 외주인원이 없는 메일은 정상적인 `외주 없음` 상태로 처리할 수 있어야 한다.

---

## 7. 신뢰도 규칙

신뢰도는 0.0~1.0으로 표현한다.

예시 가중치:

- 업체 마스터 정확 일치: +0.25
- 명시적 `외주인원` 영역 내부: +0.20
- Tracking No. 확인: +0.15
- 장비명 확인: +0.15
- 당일 레이블과 숫자 인접: +0.15
- 누적 레이블과 숫자 인접: +0.10

감점 예시:

- 숫자 후보 충돌: -0.25
- 장비 구간 분리 불확실: -0.20
- 업체 미등록: -0.15
- 전일과 동일: -0.30

임계값은 설정 가능하게 한다.

- 0.85 이상: 정상 후보
- 0.60~0.84: 검토 권장
- 0.60 미만: 검토 필요

신뢰도가 높아도 중복 또는 논리 오류가 있으면 정상 처리하지 않는다.

---

## 8. Outlook 규칙

- Outlook 2019 Desktop COM만 지원 대상
- 조회는 날짜 범위를 명시
- 제목은 보조 조건
- 담당자 이메일을 핵심 필터로 사용
- Exchange 발신자는 SMTP 주소로 변환
- EntryID를 반드시 저장
- MailItem이 아닌 항목은 건너뜀
- 원본 열기는 Outlook Inspector를 사용
- 읽음 상태를 변경하지 않도록 주의
- 폴더 경로는 설정으로 관리

---

## 9. Excel 규칙

- 개발과 테스트는 실제 파일의 사본으로 수행
- 쓰기 전에 파일 존재·잠금·읽기 전용·권한 확인
- 백업 성공 후에만 쓰기 시작
- 시트 헤더를 이름으로 매핑
- 고정 셀 주소 하드코딩 금지
- 병합 셀 영역에 직접 쓰지 않음
- 기존 수식과 서식을 가능한 한 유지
- 반영 성공 후 저장 여부 확인
- Excel 저장 성공 후 DB 처리 완료 커밋
- 실패 시 사용자에게 백업 경로와 실패 지점을 표시

---

## 10. 중복 및 수정본 규칙

### 중복

- 동일 EntryID는 동일 메일
- 동일 핵심 레코드 키는 중복 후보
- 재실행 시 기존 처리 레코드를 기본 제외

### 수정본

다음 중 하나 이상이면 수정 가능성으로 표시한다.

- 동일 보고일·발신자, 다른 EntryID
- 제목에 수정/재송부/재발송
- 동일 장비·업체 키인데 값이 다름

자동 덮어쓰기하지 않는다.
사용자가 유지·교체·별도 추가를 선택하게 한다.

---

## 11. 테스트 규칙

- 실제 개인정보가 포함된 메일을 테스트 저장소에 커밋하지 않는다.
- 익명화 fixture 사용
- parser 변경 시 회귀 테스트 필수
- 버그 수정 시 재현 테스트 먼저 추가
- Outlook/Excel COM adapter는 mock 가능해야 함
- 실제 COM 통합 테스트는 별도 marker 사용
- Excel 반영 테스트는 매번 새 사본에서 수행
- 최소 검증 항목:
  - 당일/누적 구분
  - 소수 공수
  - 한 메일 여러 장비
  - 한 장비 여러 업체
  - 외주 없음
  - 누적만 존재
  - 수정본
  - 중복 실행

---

## 12. 로그 규칙

로그 레벨:

- INFO: 정상 처리 단계
- WARNING: 검토 필요, 일부 필드 누락
- ERROR: 개별 메일 또는 Excel 반영 실패
- CRITICAL: 데이터 손상 위험, 백업 실패

로그에 포함:

- 작업 ID
- 메일 EntryID 해시 또는 일부 식별값
- 처리 단계
- 결과
- 오류 코드

로그에서 제외:

- 메일 본문 전체
- 수신자 전체 목록
- 불필요한 개인정보
- 인증 정보

---

## 13. 변경 관리 규칙

- 한 작업 단위마다 변경 목적과 파일 목록을 먼저 제시한다.
- 기능 변경과 대규모 리팩터링을 같은 커밋에 섞지 않는다.
- DB 스키마 변경 시 마이그레이션을 포함한다.
- 설정 키 추가 시 기본값과 이전 버전 호환성을 제공한다.
- 사용자 승인 없이 실제 Outlook/Excel 데이터에 쓰는 테스트를 실행하지 않는다.
- 완료 보고에는 다음을 포함한다.
  - 변경 파일
  - 구현 내용
  - 테스트 결과
  - 남은 위험
  - 다음 권장 단계

---

## 14. 완료 정의

작업은 다음 조건을 모두 만족해야 완료다.

- 요구사항 구현
- 타입 검사 또는 기본 정적 점검 통과
- 관련 pytest 통과
- 오류 처리 존재
- 로그 존재
- 사용자 데이터에 대한 안전장치 존재
- 문서 업데이트
- 실행 또는 검증 절차 보고
